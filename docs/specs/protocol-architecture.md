# 设计定稿 B：协议架构——提示词长度、阶段化与模型分层

> 文档性质：规范性设计定稿。回答"怎样让模型稳定遵守协议"这个工程问题。
> 状态：已定稿，待实现（见 [roadmap.md](../roadmap.md) P0-0 与 P1）。
> 上位文档：[consensus.md](../consensus.md) §7.3（Skill / 确定性工具 / Agent / 用户的分工）。

## 1. 问题

教学时模型需要同时遵守的规则约 560 行（主技能 SKILL.md 139 + tutoring-protocol 162 + lesson-contract 111 + prerequisite-protocol 65 + source-handling 86），全部以中文散文形式给出。已知事实：

- 指令数量增加时，单条指令的遵循率整体下降，不是线性衰减（多约束指令遵循基准的一致结论）；
- 长上下文中位于中段的内容最容易被忽略（"lost in the middle"）；
- 项目 roadmap 已经指出："当前协议依赖强模型稳定遵循一份很长的文本约束……上多模型后，协议必须从一段长提示拆成显式的编排步骤。"

更根本地：**靠加长提示词换取遵循度，是在用"说服"代替"设计"。** 每加一条规则都在期待模型读到、记住并在正确时刻应用，而系统没有任何机制知道它做没做到。这与 consensus §7.3 "能确定性检查的就不该是提示词规则"相悖。

## 2. 五条原则

1. **结构先于规则。** 凡能用 schema、文件边界或校验器表达的约束，不写成提示词。例：高层内容"不得泄漏"不靠规则，靠 `.deep.json` 在渲染阶段根本不被加载。
2. **任一时刻的有效规则集 ≤ 60 行。** 模型在某个状态下需要读的全部指令，加起来不超过一屏。
3. **阶段之间的接口是文件，不是工作记忆。** 每个阶段读若干 JSON、写一个 JSON、过一个校验器。
4. **一个好例子替代十条规则。** 每个阶段附一份真实产物片段作为范例，规则只写例子无法表达的部分。
5. **可评测。** 任何提示词改动都要能在固定的 eval 集上看到通过率变化；看不到就不改。

反面约束：**不过度拆分。** 阶段过多会丢连贯性（写讲义的阶段不知道抽概念的阶段为什么这么切）、增加编排本身的 bug 面、拉长延迟。目标是把"每时刻 560 行"压到"每时刻 ≤ 60 行"后停下，不追求更碎。

## 3. 教学协议：按状态加载

`tutoring-protocol.md` 拆为按状态机加载的小文件（纯重构，不改逻辑）：

```text
references/protocol/
├── _state-machine.md     # 15 行：状态图 + "一次回复只推进一个状态"
├── ready.md              # READY：呈现 problem，DEEPEN 判断信号
├── predict.md            # PREDICT：揭示顺序，跳过条件
├── deepen.md             # DEEPEN：zoom 文档契约与一次性限制
├── main.md               # MAIN：主问题设计清单，信心标注
├── assess.md             # ASSESS：六维评估、depth_reached 判定、verdict 表、比较器调用
├── feedback.md           # 反馈顺序、追问表、同节不重复出题、两层上限
├── resume.md             # resume 开场：变式检索、--review、去主体化命题复习
└── finish.md             # 课程结束：整体重述、迁移、总结口径
```

SKILL.md 只保留"当前处于哪个状态就读哪个文件"的一张表。每个文件 ≤ 40 行，`assess.md` 与 `feedback.md` 允许到 60 行。同样的切分适用于 `prerequisite-protocol.md`（诊断 / 补充 / 桥接三段）。

## 4. build 管线：阶段、产物、执行者

```text
S1 范围      材料 → sources.json（脚本）+ 范围说明（模型）
S2 抽取      材料 → 概念、关系、问题链候选（强模型）
S3 标注      候选 → layer、domain_path、support（强模型）
S4 定位      每条 source_ref → 原文核验（模型提议定位，脚本核验引文确实出现在该位置）
S5 外部补充  前置缺口 → 联网检索 + 带引用摘要（廉价模型）→ URL 可达、引文在页内（脚本）
S6 组装      → lesson-plan.json 1.1（模型）→ validate_lesson.py（脚本）
S7 渲染      lesson-plan → teaching-guide.md（脚本模板铺骨架，强模型只润色 problem/solution/mechanism 的叙述）
S8 导出      lesson-plan → mrg/*.json + .deep.json + index 更新（脚本）
```

- 每阶段一个提示文件（≤ 60 行 + 一个范例片段）、一个输入 JSON、一个输出 JSON、一个校验器；
- S2 与 S3 可以合并为一次强模型调用（避免抽取与标注脱节），其余保持独立；
- 校验失败只重跑失败的阶段，把校验器错误原文反馈给模型；
- 阶段间不共享对话历史；需要的上下文全部在输入 JSON 里。

## 5. 模型分层

原则：**决定 MRG 正确性和 LRG 判定的地方不省，其余全省。**

| 任务 | 执行者 | 理由 |
|---|---|---|
| 来源清单、哈希、引文定位核验 | **脚本** | 完全确定性 |
| 教学包结构校验、LRG 泄漏检查、比较器类别落定 | **脚本** | 已有或规则明确 |
| 联网检索 + 带引用摘要 | **廉价模型 + 脚本核验** | 弱模型更易编造引用；URL 可达与引文在页内必须由脚本检查 |
| 概念 alias 召回、跨课索引匹配 | 脚本召回 + **廉价模型**确认 + 人工确认歧义 | 召回可粗，精确靠确认 |
| teaching-guide 骨架 | **脚本模板** | lesson-plan 的格式化，不需要生成 |
| 抽概念、**定关系类型与方向**、标 `layer` | **强模型** | MRG 质量的全部所在；"默认可信"的前提 |
| 逐节评估、追问生成、`depth_reached` 判定、命题抽取 | **强模型** | 教学质量核心；一次误判就进 LRG 且不可改 |
| 讲义叙述润色 | 强模型 | 面向学习者的最终文本 |

### 5.1 宿主支持

- **Claude Code**：插件可在 `agents/*.md` 定义子代理，frontmatter 支持 `model: haiku | sonnet | opus | inherit`。S5、S4 的模型部分、alias 确认可各自声明为独立子代理并指定廉价模型；主对话模型由用户控制，技能不切换它。
- **Codex / DeepSeek Harness**：按宿主文档确认是否有等价的按任务指定模型机制；**未确认前不假设**。回退策略：这些阶段在该宿主上用主模型执行，同一份技能目录不变。
- 分层的前提是 §4 的阶段化——一段推理做完所有事时无从降级。

## 6. eval 集

在 `plugin/evals/` 建最小 eval 集，任何提示词或阶段划分改动都跑一遍：

- **材料**：三份类型不同的小材料（一个教材章节、一个小代码库、一篇论文），各 ≤ 30 KB；
- **build 指标**：`validate_lesson.py` 通过率；小节数落在 4–9；每节概念数 ≤ 4；`support` 分布（`unsupported` 比例）；`relations[]` 端点存在率；`layer` 标注人工抽查一致率；引文定位核验通过率；
- **teach 指标**（脚本化对话回放）：一次回复是否只推进一个状态；首次重建前是否出现 criteria 文本；追问是否引用了回答内容；`depth_reached` 与人工判定的一致率；
- **成本指标**：每阶段 token 用量，强模型调用次数。

宿主已提供 skill-creator 一类的 eval 框架时优先复用；否则用 unittest + 固定 fixture 实现。eval 结果不追求绝对值，追求"改动前后可比"。

## 7. 实施顺序

1. §3 的按状态拆分（纯重构，零逻辑变更，立即可做，同时验证三个宿主的渐进加载都可用）；
2. §6 的 eval 集（有了它才能安全做后面的事）；
3. §4 的 S6–S8（组装、渲染、导出）——它们最接近现有脚本；
4. §4 的 S2–S5 与 §5 的子代理声明；
5. 观察 eval 曲线，决定是否继续拆。
