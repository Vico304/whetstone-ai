# 术语表与写作规则

本文件是仓库文档的用语标准。两套用语对应两类读者：手册用语给使用者，设计用语给维护者和想理解设计的人。两套用语说的是同一个东西，本表是它们之间的对照。

## 1. 两套用语

| 手册用语（README、guide） | 设计用语（design、specs、代码） | 含义 |
|---|---|---|
| 参考图 | MRG（machine reference graph）；知识库目录 `mrg/` | 系统从材料抽出的知识框架：概念、关系、每条主张的来源定位，分四层。评估回答时以它为尺子 |
| 学习记录 | LRG（learner reconstruction log）；`lrg/<lesson-id>.jsonl` | 每次作答的只追加日志：原文、模型抽取、与参考图的差异、判定、到达的层。学习者不能看、不能改 |
| 来源、来源定位 | SEL（source evidence layer）；`sources.json`、`source_refs[]` | 材料文件清单（含 SHA-256）和每条主张指向材料的位置与来源类型 |
| 四层：事实、机制、本质、思想 | `fact / mechanism / rationale / principle` | 理解的四个层次。前两层可以展示，后两层只用来出题和判断回答到了哪一层 |
| 核心、辅助、仅列出、略过 | `core / supporting / listed / deferred` | 一节里概念的角色：核心进主问题，每节最多 4 个，超出降为辅助；辅助会讲、可要求验收；仅列出只给名字和一句定义；略过留到以后 |
| 完整、快速 | `mode: full / fast` | 一门课的严格程度。快速缩小范围、放宽判定，但仍然先预测后揭示 |
| 人造系统、自然现象 | `subject: designed / natural` | 这批材料讲的东西有没有设计者。有设计者时"为什么这样做"有真实答案，问题链按限制 → 方案 → 代价推进；没有设计者时只能问哪个模型解释它、用了什么简化、什么证据能区分 |
| 按材料学、按领域学 | `orientation: material / domain` | 课程范围由材料的结构决定，还是由领域的原理结构决定 |
| 骨架课、分支课、普通课 | `shape: skeleton / branch / linear` | 按领域学时先学一门只讲原理的骨架课，学完从分支候选里选方向，每个分支是一门分支课 |
| 落点 | `anchor` | 骨架课里一个概念在你的材料中的一处位置 |
| 探测题 | `probe` | 骨架课每节一道无提示的原理题，教学前作答；答对的节由你决定是否跳过 |
| 主问题 | `checkpoint` | 每节读完后要回答的问题；判定标准 `criteria` 不展示 |
| 来源类型：原文明示、可推出、外部知识、教学推断、无依据 | `support: explicit / entailed / external / pedagogical_inference / unsupported` | 一条主张的依据从哪来。教学推断在评估时降权，与它冲突不判错 |
| 把握：有把握、没把握、不知道 | `confidence: 5 / 3 / 1` | 作答前学习者自报的三档；只作诊断信号，有把握且错的优先反馈 |
| 时效：有效、过期、未知 | `freshness: fresh / stale / unknown` | 一个概念的掌握证据是否还在有效期内。只有当场答对的证据记为未知 |
| 概念索引 | `concepts/index.json` | 跨课程的概念 id、别名、出现记录 |
| 掌握状态 | `learner-state.json` | 从学习记录派生的每个概念的状态：证据强弱、时效、到达过的层、错误说法、信心校准 |
| 外部资料存档 | 外部存档；`<工作区>/external/<集名>_<日期>/` | 模型检索来的资料先存成材料集再引用；引用标 `external` |
| 前置课、前置栈 | 前置课（`prerequisite_of / blocked_at / depth`，schema 1.4）；前置栈（`learning-plan.md` §3a） | 为父课的缺口建的一门普通课，父课在被卡的节等它；栈记录每一层与回程 |
| 下一步清单、假性掌握 | `fringe.outer / fringe.suspect`（`learner-state.json`） | 由前置关系和掌握状态算出：前置都已掌握而自身未掌握的概念，是下一步；自身已掌握而某个前置薄弱的概念，是假性掌握 |
| 链重建 | `comparator.py --chain`、事件的 `chain`、`lessons.<id>.chain_rebuild` | 学习者说出概念之间的关系，与参考图的关系集逐条比对；对上的边占参考边的比例是链重建比例 |
| 易混对 | `contrast: {with, differs_in}`（schema 1.5） | 一个概念最容易与之混淆的近邻，以及差在哪个变量 |
| 对比案例 | `cases[2]` | 两个表面不同、结构相同的例子，讲义先摆它们再揭示机制 |
| 本体类别 | `ontology: entity / process / constraint / relation` | 一个概念是东西、过程、约束还是关系；答错类别时要重新归类，不是反驳 |
| 有争议的取舍 | `tradeoffs[].contested` 与 `sides[]` | 材料在这一点上说法不一，两方各有来源 |
| 结构讲解节、过程讲解节 | `sections[].kind: structure / process`（schema 1.6；缺省 `chain` 即问题链节） | 结构讲解节说清系统由哪些部分组成、谁包含谁、谁连谁；过程讲解节追踪一种明确的运行方式，一步一步说清谁做了什么、什么变了。两者都没有"方案"和"引出的新问题" |
| 系统结构图 | `big_picture.system_map: {components, links}`（schema 1.6） | 部件清单与它们之间带文字说明的连线；部件就是本课的概念，`parent` 表示包含。旧的步骤列表形式仍然接受 |
| 返回位置 | `sections[].position`（schema 1.6） | 这一节展开的是系统结构图上的哪个部件 |
| 图宽预算 | `mermaid_fit.py --width`，默认 96 列 | 一张图在笔记宽度里还看得清的上限，按等宽列数算，全角字符算两列。超出时按固定顺序收窄：折节点名、折边标签、剥掉与端点重复的标签、把有跨界边的子图画成盒子 |
| 子节 | `sections[].parent_section` | 深化某一节的节，在原节稳固之后学 |
| 依赖类型 | `dependency_kind: def / mech / tool` | 前置缺口缺的是定义、机制还是表征或操作，决定补法 |
| 复习课 | `shape: review`、`review_of[]`、`review_kind: repeat / deepen` | 为已学过的一门或几门课建的课，侧重薄弱处，先作答再揭示；子节在这里学 |
| 事实卡 | `cards/<lesson-id>.json`、`kind: recall` | 事实层与仅列出的概念的名字对定义，按到期复习；只落在那个概念上，不给机制、本质、思想做卡 |
| 接缝题 | 复习课结课的迁移题（`review_of` 多于一门时） | 一个必须同时用到两门课机制的情境 |

规则：

- 手册里不出现右列任何一个词。字段值、目录名、文件名只在使用者需要输入或查看文件时以代码字体出现，不当作词汇使用。
- 设计文档和 specs 里用右列，首次出现给一次左列的中文，之后直接用。
- 两列各自内部不换说法：手册里"参考图"不再写成"参考答案""知识图谱"；设计里 MRG 不再写成"机器参考图"。
- 英文 README 用左列的直译：reference graph、learning log、the four layers、core / supporting / listed、full / fast、by material / by domain。

## 2. 不再使用的词

这些词在旧文档里承担过定义作用，现在一律改成描述系统行为的句子。

| 旧词 | 改为 |
|---|---|
| 去主体化命题 | 旧回答里的错误说法以匿名形式重新出现："有一种说法是……这个说法哪里有问题？" |
| 到达层 | 这次回答到了哪一层；字段 `depth_reached` 只在 specs 出现 |
| 变式题替代诊断 | 已学过的概念用一道变式题代替重新诊断 |
| 覆盖账本 | 覆盖表：材料的每个标题分到了哪一节、什么角色，或为什么略过 |
| 单向诊断比较 | 对照参考图找出回答里的遗漏、错误和新增 |
| 提示渐隐 | 提示逐步减少 |
| 证据等级链 | 证据强弱：当场答对 < 隔一夜之后答对 < 隔一夜之后换一个情境答对 |
| 不透明原则 | 系统不展示的两样东西：参考图的后两层，你自己的学习记录 |
| 结构先于规则 | 能用文件结构、schema 或校验器表达的约束，不写成提示词 |
| 规范性基线、共识 | 不再有"规则冲突时的权威文档"。行为以代码和校验器为准，design.md 只说明设计意图 |
| 主动重建、重建 | 手册："用自己的话讲一遍"；设计文档可用"重建" |
| 教学包、课程包、学习包 | 课程目录 |
| 小节、unit | 节；目录名 `units/` 以代码字体出现 |
| 宿主 | 手册：直接写工具名（Claude Code、Claude Desktop、Codex、DeepSeek Harness）；设计文档可用"宿主" |
| 学习者 | 手册用"你"；设计文档用"学习者" |
| 前置诊断 | 前置检查 |
| 认知负担上限、可承受的局部子图 | 每节最多 4 个核心概念 |
| 证据池、保留项 | 手册：材料池、备用材料；specs：`pool / reserve` |
| 概念注册表 | 概念索引 |
| 学习者状态 | 掌握状态 |
| 就地学、统一管 | 独立布局、统一布局（工作区的两种布局） |
| 知识库目录（指统一布局的根） | 总目录；"知识库"只指 `store/` |

## 3. 写作规则

1. 只写代码里存在的行为，用现在时。每条行为能对到 `plugin/` 里的一个文件或一条校验规则。没实现的不写。
2. 先说系统做什么，再说为什么。不写"X 是一种……对象"式的定义。
3. 一个概念一个名字，同一文档里不换说法。
4. 英文只出现在代码字体里：字段名、字段值、文件名、命令。
5. 引用最多一跳：链到文件或标题，不写"见 §x.y 与 §z"。
6. 句子短，不嵌套括号，不用加粗强调。
7. 数字带出处：效应量、命中率、行数都写明来自哪里。
8. 不写营销语。专业的意思是准确、可核对、术语一致。
9. 长度上限：README ≤ 120 行，guide ≤ 350 行（含示例对话），design ≤ 250 行，每份 spec ≤ 200 行。
10. 以上第 1–4、9 条由 `check_docs.py` 检查（断链、手册里的设计用语、旧词、长度），CI 每次运行；AI 会话的规则在仓库根的 `AGENTS.md`。

## 4. 每份文档的读者

| 文件 | 读者 | 用语 |
|---|---|---|
| `README.zh-CN.md` | 第一次看到项目的人 | 手册用语 |
| `README.md` | 同上，英文短版 | 手册用语的英译 |
| `docs/guide.md` | 使用者 | 手册用语 |
| `docs/design.md` | 想理解设计的人、维护者 | 设计用语 |
| `docs/specs/*.md` | 维护者；内容可对照校验器核对 | 设计用语 |
| `docs/evidence.md` | 想核对依据的人 | 设计用语 |
| `CHANGELOG.md` | 所有人 | 手册用语；字段以代码字体出现 |
| `plugin/skills/**` | 模型 | 不在本规则范围内 |
