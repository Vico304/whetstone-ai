# 示例：从总体问题理解系统设计

## 如何使用这份文档

先阅读一个小节，再在不照抄正文的情况下回答该节末尾的问题。回答后再查看反馈并进入下一节。讲义只给出每节的问题、方案与机制；它的意义、代价与设计理由留给你在回答中自己得出。

## 材料范围与不确定性

- 来源：`examples/source.md`
- 已覆盖：总体设计与核心流程
- 未覆盖：部署和性能调优
- 不确定性：示例来源没有说明长期存储策略

## 总体问题

材料试图解决：如何把分散输入转成可以理解和验证的结果。

## 宏观流程

```text
输入范围 → 结构分析 → 教学路径 → 学习者解释 → 反馈与迁移
```

## 问题链预览

1. 原始材料是线性的，难以看出整体结构。
2. 结构图能展示组件，但又无法解释组件为何存在。
3. 问题驱动叙事给出理由，但阅读仍不等于掌握。
4. 逐节解释让理解外显，随后才能诊断和迁移。

## 1. 从线性材料到总体结构

### 当前问题

逐页或逐文件阅读会让局部信息遮住系统要解决的总体问题。

### 解决方案

先建立输入、关键过程和输出的宏观地图。

### 工作机制

宏观地图把分散内容压缩成少数功能步骤，使后续细节能挂接到明确位置。

### 它引出的新问题

结构只能说明“有什么”，不能说明“为什么必须这样设计”。

### 关键概念

- **系统边界**：本次解释纳入和排除的输入、过程与输出。
- **宏观地图**：为细节提供位置的最小端到端流程。

### 来源

- `examples/source.md`，`## Architecture`（`explicit`）：来源直接列出主要步骤。
- 课程先讲总体结构（`pedagogical_inference`）：这是教学顺序，不是来源的事实主张。

### 轮到你解释

为什么直接按文件顺序阅读容易失去整体意义？宏观地图解决了什么，又没有解决什么？

## 总结与迁移挑战

请脱离上面的编号，重新说明问题如何一步步推动方案演化。然后选择一个你熟悉的项目，说明你会怎样先画出它的宏观地图。
